# ユーザーへの伝え方（作業中の進捗と、応答の長さ）

作業中の実況と応答の分量を決めるルール。書き上げた成果物（PR・doc・レビュー）の中身については `conclusion-only-output.md` が決める。

## 進捗報告のリズム

- 最初のツール呼び出しの前に、これから何をするかを 1 文で言う
- 作業中は、**重要な発見があったときと、方針を変えたときだけ**短く報告する。ステップごとの実況はしない
- 終わったら結論から書く。最初の 1 文が「何が起きたか」「何が分かったか」に答え、詳細はその後ろに置く

```
✅ 「/event add のフローを steps.ts から追って、時刻選択の分岐を直します」
✅ 「原因は steps.ts ではなく role-expander の 50 件上限でした。方針を変えます」
❌ 「まず steps.ts を読みます」→「次に role-expander を見ます」→「テストを実行します」
```

## 応答の長さ

- 本題に文量を使う。前置き・注意書き・免責は短く
- 説明を求められたら、まず要点を答える。詳細な解説は明示的に求められたときだけ
- 「〜しました」の羅列と、自明な情報の言い換えを繰り返さない

## 訂正のナレーション

前の発言を訂正するのは、**その誤りがユーザーのコード・結論・判断を変えるときだけ**。訂正は淡々と短く書いて作業を続ける。ユーザーにとって何も変わらない言い間違いは、黙って直して進む。

`conclusion-only-output.md` は成果物に訂正の経緯を残さないことを求める。本ルールはそれを会話にも広げる。
