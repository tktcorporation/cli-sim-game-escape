# ゲーム開発とシミュレーション開発をセットで行うルール

新しいゲームを追加する、または既存ゲームのバランス（数値・確率・コスト・敵の強さ等）に
影響する変更を行う際は、必ず `src/games/<game>/simulator.rs` に自動プレイシミュレーターを
実装または拡張し、コード変更とセットで行う。目視のプレイテストだけでは「詰み確率」
「平均所要時間」のような統計的な体感は検証できない。

## 既存の実装パターン

このリポジトリの全ゲームが既にこのパターンに従っている:

- `src/games/cookie/simulator.rs` — 最適購入戦略のbotで1時間/2時間プレイし、
  `eprintln!` で進行状況をレポートする
- `src/games/metropolis/simulator.rs` — AIの自動プレイを1時間走らせ、
  「建設が止まらない」「worker数を増やすと完成数が増える」等を assert する
- `src/games/loopmarch/simulator.rs` — 大量のシード試行で「初回の手札補充成立前に
  死亡する確率」のような統計的バランスを検証する

## 構成要素

`#[cfg(test)] mod tests`（または `#![cfg(test)]` なファイル）の中に:

1. **自動操作関数**: 拠点で買えるものを買う・手札を配置する・補充する、といった
   「典型的なプレイ」または「最適プレイ」を模した bot 関数
2. **レポート関数**: `eprintln!` で状態を出力する。`cargo test <game>::simulator --
   --nocapture` で実行すると人間が読めるレポートになる
3. **不変条件を assert する `#[test]` 関数**: `#[ignore]` にせず、通常の `cargo test`
   で継続的に実行される回帰テストにする。「ゲームが永久に停止しない」「詰み確率が
   閾値を超えない」など、バランス崩壊を検知できる具体的な閾値を置く

## いつ書くか

- **新規ゲーム追加時**: 最低1つ、長時間の自動プレイで panic せず・進行が止まらない
  ことを検証するテストを書く（`long_run_never_panics_and_keeps_invariants` 相当）
- **バランス調整時**: 変更前の数値をシミュレーションで実測してから調整方針を決める。
  「たぶんこれくらいで直るはず」で数値を変えて終わらせない。調整後も再実測し、
  改善を確認してから確定する。妥当性を示す統計的な回帰テストを残す
- **バグ報告への対応時**（「◯◯ができたことがない」等の体感クレーム）: 主観の
  訴えをそのまま信じるのでも、そのまま無視するのでもなく、まずシミュレーションで
  実際の発生確率・所要時間を数値化してから対処する
