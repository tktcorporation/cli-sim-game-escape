# PR 作成前のセルフレビュー必須ルール

## 背景

Claude が作成した PR は、作成直後にセルフレビューを回すとほぼ確実に修正すべき問題が見つかる。2回レビューを回すと精度が大幅に上がる。

## 仕組み

`gh pr create` は PreToolUse フック（`.claude/hooks/require-pr-self-review.sh`）でブロックされる。セルフレビューを2回完了するまで PR は作成できない。

## 手順

PR を作成したいとき、以下を自動的に実行する:

### 0. plan / spec 消費チェック

変更が `docs/plans/` `docs/superpowers/plans/` `docs/superpowers/specs/` の設計を実装するものか確認し、消費してよいかを `doc-placement.md` の寿命の節の手順で判断する。このステップは hook による強制対象外なので、都度手動で確認する。フォローアップ TODO が残るという理由で plan / spec を残したまま PR を作成した場合、以後そのままの PR に追加コミットで残タスクを終わらせることがある。マージ前にこのチェックを再実行し、消費できる状態になっていないか確認する。

### 1. セルフレビュー（1回目）

```bash
codex review --uncommitted
# OR
/superpowers:requesting-code-review
```

結果を確認し、指摘事項があれば修正する。

### 2. レビュー完了を記録

```bash
bash .claude/hooks/record-pr-review.sh
```

### 3. セルフレビュー（2回目）

1回目の修正を反映した状態で再度レビューする:

```bash
codex review --uncommitted
# OR
/superpowers:requesting-code-review
```

再び指摘事項があれば修正する。

### 4. レビュー完了を記録

```bash
bash .claude/hooks/record-pr-review.sh
```

### 5. PR 作成

2回のレビューが完了していれば `gh pr create` が通る。

## レビュー指摘への対応方針

**見つけたものは全て報告する。「問題ありませんでした」で済ませない。**

レビューで完全に問題がないことはほぼありえない。軽微なものでも見つけた事実を報告し、修正するか・あえてしないかを判断と理由付きで伝える。

| 重要度           | 対応                                                                           |
| ---------------- | ------------------------------------------------------------------------------ |
| Critical / Major | 即座に修正                                                                     |
| Minor            | 積極的に修正する。あえて修正しない場合は理由を明記して報告                     |
| Suggestion       | 修正するか、「こういうのを見つけたが、〇〇の理由で今回は修正しなかった」と報告 |

### 報告フォーマット

修正した指摘だけでなく、あえて修正しなかったものも含めて報告する:

```
## レビュー結果
### 修正した指摘
- [内容と修正内容]

### 見つけたが修正しなかったもの
- [内容] — 修正しなかった理由: [理由]
```

### アンチパターン

- 「特に問題ありませんでした」とだけ報告する → 何を見て何を判断したか不明
- 軽微な指摘を黙って無視する → 見つけた事実自体を報告する
- 全部直して報告にだけ「問題なし」と書く → 何を直したかも書く

## 注意

- レビュー回数のカウンターは `.claude/.pr-review-count` に記録される（gitignore 済み）
- PR 作成が許可された時点でカウンターは自動リセットされる
- `codex review` が使えない環境では、Agent ツールの code-reviewer サブエージェントを代替として使う
