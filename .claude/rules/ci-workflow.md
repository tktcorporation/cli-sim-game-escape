# CI / PR ワークフロー

push 前に CI をローカルで再現し、push 後は全チェックが pass するまで見届ける。どちらも「たぶん大丈夫」で飛ばさない。

## push 前: CI をローカルで再現する

1. `.github/workflows/` の全ワークフローを読み、`push` / `pull_request` トリガーで走る `run:` コマンドをすべて列挙する
2. そのうちローカルで実行できるものを特定する
3. 全部実行する。1 つでも fail したら修正して再実行する
4. 全 pass を確認してから push する

ローカルで実行しなくてよいのは次だけで、これ以外は省略しない。

- CI 固有の secret / 環境変数が必要なコマンド（エラー監視サービスへの upload 等）
- GitHub API 操作（PR コメント投稿、ラベル付与）
- E2E テスト（明示的に求められたときだけ実行する）
- Docker や CI 固有環境でしか動かないコマンド

典型的な対象は lint・format・型チェック・test・未使用コード検出・ライセンスチェック・ビルド・changeset の有無。生成物と SSOT の乖離検知のようなプロジェクト固有のチェックがワークフローにあれば、それも実行する。

## push 後: CI が pass するまで見届ける

1. `gh pr checks <PR番号> --watch` で全チェック pass まで監視する
2. fail したら `gh run view <run-id> --log-failed` でログを読み、原因を特定する
3. 修正して push し、再度監視する
4. 全チェックが pass するまでこのサイクルを回す

**全チェックが pass するまでユーザーに「完了」と報告しない。**

失敗が自分の変更と無関係だと判断したときは、その根拠（base branch でも再現する / ローカルで再現しない / 失敗箇所が差分に触れていない）を示す。根拠なしに flake と断定しない。

## changeset

changeset を使うプロジェクトでは、その CI が何を要求するかを確認して従う。全 PR に新規の `.changeset/*.md` を要求する CI なら、ドキュメントのみ・リファクタなど版に影響しない変更でも、frontmatter を空にしたファイルを追加して bump 無しを表明する。要求しない CI なら、版に影響する変更のときだけ追加する。bump するパッケージ名は `package.json` の `name` を参照する。

確認先は「変更を出す先のリポジトリ」の CI 設定になる。サブモジュールや別リポジトリで作業しているときは、手元のワークスペース直下の `.github/workflows/` を見てもその要求は分からない。

## 禁止事項

- CI チェックを通さずに push する
- lint エラーを disable コメントで安易に抑制する（正当な理由がある場合は理由を明記する）
- テスト失敗を無視して push する
- 「たぶん大丈夫」で push する（実行して確認する）
