# PR レビュー・修正ループ

PR作成前のローカルブランチ差分に対して、`pr-deep-review` のレビューと `upstream-fix` の根本原因修正を、指摘が収束するまで繰り返すスキル。1回のレビュー→修正では終わらせず、指摘が出なくなる(または直しても変わらなくなる)まで自動的にループする。

## 何のためのスキルか(位置づけ)

```
pr-deep-review          →  1回のレビューで4レンズの指摘を出す
upstream-fix             →  1件の修正依頼に対する根本原因分析(症状→直接原因→根本原因→A/B/C提案)
pr-review-loop(本スキル)  →  上記2つを「指摘全体」に対して収束するまで繰り返す
```

本スキルは `pr-deep-review` の手順そのものは変更しない。`upstream-fix` の Phase 1-4 の視点も変更しない。変えるのは適用範囲で、upstream-fix を**1件の指摘ではなくラウンドの指摘全体**に対して適用し、それを複数ラウンド繰り返す。

**`.claude/rules/pr-self-review.md`(`gh pr create` 前の `codex review --uncommitted` 2回ゲート)とは別物。** 本スキルが収束しても、PR作成前には従来どおりこのゲートを満たす必要がある。観点が異なる(本スキルは4レンズの構造化レビュー、codex reviewは汎用の軽量チェック)ため、両方やる意味がある。

## いつ使うか

- 「収束するまでレビューと修正を繰り返して」「指摘がなくなるまで直して」といった明示的な依頼
- 複数回のレビュー→修正を繰り返す前提の、PR作成前の仕上げ作業

**使わなくてよい場面**: 「深くレビューして」だけの依頼(`pr-deep-review` 単体で足りる)。1件だけの明確なバグ修正依頼(`upstream-fix` 単体で足りる)。

## 手順

### Step 0: スコープ確定

```bash
git fetch origin main
git diff origin/main...HEAD --stat
git diff origin/main...HEAD
```

ラウンド数カウンタ = 0、前ラウンドの Step 3 クラスタ診断結果 = 空、として開始する。

### Step 1: レビュー(ラウンドごとに専用サブエージェント)

`Agent` ツールで、現在の差分を `pr-deep-review` の手順でレビューするサブエージェントを起動する。

```
Agent: "以下の差分を pr-deep-review スキル(.claude/skills/pr-deep-review/SKILL.md)の
手順でレビューせよ。差分: <git diff origin/main...HEAD の内容>
狙い(基準線): <イシュー/PRの狙いが分かれば>

指摘を file / summary / severity(Critical/Important/Minor) / category
(spec-mismatch / correctness / code-quality / design-consistency) の
構造化リストで返せ。レビューの詳細な思考過程は返さず、指摘リストだけを返すこと。"
```

レビューの詳細はサブエージェント内に閉じ、メインセッションには指摘リストだけを持ち帰る。ラウンドを重ねてもメインのコンテキストは膨らまない。

### Step 2: 収束判定

- 今ラウンドの指摘が0件 → **収束**。Step 7へ
- 今ラウンドの指摘が指し示す根本原因を、**前ラウンドの Step 3 で診断したクラスタ**と比較する(素の指摘リストの文字列同士を比較しない)。指し示す根本原因が前ラウンドから変わっていなければ**意味的に同じ**とみなす(文言の揺れは同一とみなす) → **途中収束**(直しても変わらない状態)。Step 7へ
- どちらでもなければ Step 3 へ

### Step 3: クラスタリング&診断(指摘"全体"に対して行う)

`upstream-fix` の Phase 1-3 の視点を、今ラウンドの指摘**全件**に横断的に適用する。1件ずつではなく、まとめて見る。

1. 各指摘の直接原因を洗い出す
2. 同じ設計上の原因(責務配置・データ正規化不足・契約の曖昧さ・抽象化不足)から出ている指摘をグループ化する
3. 「これを1箇所直せば複数の指摘がまとめて消えるのでは」を探す。他と関連しない指摘は無理にまとめず単独クラスタのままでよい
4. このラウンドのクラスタ診断結果は、次ラウンドの Step 2 の比較対象として保持しておく

### Step 4: 修正方針決定(クラスタごと)

`upstream-fix` の判断基準に従い、クラスタごとに A(フル改善)/B(上流修正)/C(局所修正)を選ぶ。

- デフォルトは **B(上流修正)**
- C(局所修正)は「同じ種類の問題が他に無い」と確認できた場合のみ許容する
- クラスタの規模が A 相当(既存コードの大きな再設計)まで見えたときは、黙って進めずユーザーに提案して確認してから着手する

### Step 5: 修正実行

**メインセッションで** Edit する(サブエージェントに丸投げしない。Step 3/4 の診断・判断根拠を保持したまま直す)。1クラスタ=1つの筋の通った変更として実装する。指摘ごとにバラバラに直さない。

### Step 6: ラウンド継続判定

ラウンド数カウンタ += 1。

- 上限(デフォルト5)未満 → Step 1 へ戻る(Step 0 のコマンドで差分を再取得する。修正前の古い diff を使い回さない)
- 上限に達した → `AskUserQuestion` で続行するか確認する。このラウンドまでの指摘推移(何件→何件)と、まだ収束していない理由を添えて聞く

### Step 7: レポート

ラウンドごとに「どの指摘に対して」「どんな根本原因を見つけて」「どう直したか」を時系列でまとめる。`.claude/rules/conclusion-only-output.md` に従い、試行錯誤の過程(捨てた案等)は書かず、確定した対応だけを書く。途中収束で指摘が残っている場合は、ユーザー判断事項として明記する。

最後に「準備完了」と伝える。`gh pr create` 前の `codex review --uncommitted` 2回ゲートは別途必要。

## 出力フォーマット

判定ラベルは Step 2 / Step 6 の結果に対応する: 収束→準備完了、途中収束→途中収束(要判断)、上限到達→中断(上限到達)。

```markdown
## PRレビュー・修正ループ: [対象ブランチ]

### 判定: 【準備完了 / 途中収束(要判断) / 中断(上限到達)】

### ラウンド別サマリ
| ラウンド | 指摘件数 | 見つけた根本原因 | 対応 |
|---------|---------|-----------------|------|
| 1 | 3件 | [クラスタの根本原因] | [B: 上流修正の内容] |
| 2 | 0件 | - | 収束 |

### 残っている指摘(途中収束の場合)
[file / summary / なぜ直せなかったか]
```

## やりがちな失敗

| 失敗 | どうするか |
|------|-----------|
| 指摘が出るたびにその指摘だけを消す最小パッチを逐次当てる | Step 3 のクラスタリングを飛ばした兆候。ラウンドの指摘全体を並べ直してから修正に入る |
| クラスタ診断でAが見えているのに確認なしでCに留める | upstream-fix と同じ理由でNG。A相当が見えたら黙って進めずユーザーに提案する |
| 指摘セットの比較を文字列完全一致でやろうとする | 同じ根本原因を指していれば文言の揺れは同一とみなす。意味的に判断する |
| 上限に達しても確認せず回し続ける、または黙って諦める | Step 6 のとおり `AskUserQuestion` で必ずユーザーに確認する |
| レポートに各ラウンドの試行錯誤・捨てた修正案を書く | `conclusion-only-output.md` 違反。確定した対応だけを書く |

## 関連ルール

- `.claude/skills/pr-deep-review/SKILL.md`: 毎ラウンドのレビュー手順そのもの
- `.claude/skills/upstream-fix/SKILL.md`: クラスタごとの根本原因分析・修正方針決定
- `.claude/rules/conclusion-only-output.md`: レポートは結論だけを書く
- `.claude/rules/pr-self-review.md`: `gh pr create` 前の別ゲート。本スキルの収束では免除されない
